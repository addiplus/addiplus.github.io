PRD Engine

Evidence: Worked example

Multi-agent workflow · Claude Code plugin

Research agents read the codebase in parallel, a synthesizer writes the spec, and at the default tier five adversarial reviewers attack the draft before anyone builds from it.

It installs from its own plugin marketplace (/plugin marketplace add addiplus/prd-engine, then /plugin install prd-engine@addiplus) and ships 10 agent definitions, a pipeline skill and four intensity tiers, from 4 agents to 19.

The repo includes one worked example, a CSV export button for a small React dashboard. It illustrates the pipeline’s output; in the repo’s words it is “not a transcript of an automated end-to-end run” (demo/README.md:9).

From the worked example: the line its review changes

The fix is recorded in §17 as a finding to apply during implementation; the requirement’s own code block keeps the drafted line.

demo/input/feature-request.md

  1. Line 12Write a PRD for adding a CSV export button to the dashboard tableThe request as typed
  2. Line 36Only the rows currently visible. What you see is what you download.A clarification answer

Step 1 of 4 · Ground

Find the two ways the obvious export goes wrong.

The example’s PRD names two traps in the sample component:

“An export wired to rows silently disagrees with the screen.”

PRD.md:57

“An export skipping format writes 12.5 where the table shows $12.50.”

PRD.md:61–62

So the spec exports visibleRows as displayed, not the unfiltered rows prop.

Step 2 of 4 · Specify

Make “it works” countable.

  • 50 rows, no filter51 CSV lines
  • Filter matches 3 rows4 lines
  • Filter matches 0 rowsButton disabled, no file

Acceptance criteria AC-03 and AC-05, PRD.md:351, 353

The example’s validation report rejects revision 1 on two blocking issues, including:

“Revision 1 said Files Touched: 3 because it counted src/utils/formatters.js, which is read but never modified.”

research/09_validation.md:27–28

Step 3 of 4 · Challenge

Five review reports attack the draft. Two find the same hole.

The data-integrity and UX-regression reports both flag a download with no byte order mark, so a spreadsheet that guesses the encoding can corrupt non-ASCII names. The UX report:

“the click succeeds, the file saves, the row count is right, and the data is quietly wrong in exactly the column that carries human names.”

research/expert_3_ux_regression.md:59–60

Two reports on one target escalate it to DANGER (PRD.md:546).

Step 4 of 4 · Resolve

Fix the download, not the serializer.

The changed line is shown above the steps.

“The mark is added in downloadCsv and not in toCsv, so every string assertion in REQ-42.01 and REQ-42.02 stays byte-exact”

PRD.md:578–579

Registry Radar

Evidence: Live demo

Full-stack app · Next.js 16 · React · TypeScript

A live Next.js app that puts npm and GitHub signals for a package scope in one view: downloads, publish history, stars, open issues and CI status.

  • Server-side proxies. The browser never calls npm or GitHub directly, so an optional GitHub token stays on the server.
  • Rate limits as state. When GitHub’s budget of 60 requests an hour without a token runs out, a banner counts down to the reset instead of the page failing.
  • Optimistic edits. Pins and notes update at once and roll back on error.

Batch Invariance Verifier

Evidence: Recorded live run

LLM inference testing · Python · llama.cpp

An evaluation harness for local LLM servers: it checks that llama.cpp returns the same scored answers when requests share a batch as when they run one at a time. Its recorded live run on phi-4 found 1 of 48 that changed, by one code comment.

It runs against llama.cpp or another OpenAI-compatible server. Matches must be exact, so even a comment-only change is RED, by design.

Read the certificate on GitHub (external site)Batch Invariance Verifier on GitHub (external site)

Sources and limits

Limits

  • One model, one context size, one batch size, one GPU host. The certificate says it does not generalize.
  • A GREEN result would only mean no divergence was detected, not that a server is batch-invariant.
  • The serial and slot-control runs agree on every scored answer; one token-level difference between them did not change a scored answer.
